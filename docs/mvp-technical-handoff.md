## 1. Текущее состояние в одном абзаце

Mathforces — монолитное full-stack PWA-приложение на Next.js с PostgreSQL, отдельным
worker-процессом и файловым object-storage-адаптером. Реализован путь от регистрации и выбора
организации до участия в контесте, загрузки фото, фоновой двухэтапной оценки, live-таблицы, ручной
модерации и рейтинга. Есть админ-панель, аудит действий, мониторинг, публичная таблица рейтинга,
кастомизируемый профиль, темы и PWA-режим. При этом автоматическая проверка математической
корректности пока является честно обозначенной локальной эвристической заглушкой: Tesseract
распознаёт текст, а балл выводится из структурных признаков. Это главный продуктовый разрыв до
полноценного MVP для реальных соревнований.

## 2. Фактический технологический стек

### Runtime и frontend

- Node.js 24 или новее;
- Next.js 16.2.10, App Router, React Server Components и Route Handlers;
- React 19.2.7;
- TypeScript 5.9 в strict-режиме;
- Tailwind CSS 4.3 через PostCSS;

- Lucide React для иконок;

- Web Animations API используется для FLIP-анимаций таблиц;
- SSE используется для live-таблицы контеста и общего рейтинга.

Рекомендованные исходным ТЗ shadcn/ui, Framer Motion, Zustand, TanStack Query и Recharts не
установлены. Для текущего размера MVP это осознанное упрощение: серверные данные загружаются в
Server Components, локальное состояние хранится в React, а live-обновления реализованы напрямую
через EventSource. При росте числа интерактивных сценариев TanStack Query может стать полезен, но
сейчас его добавление не даст автоматической архитектурной выгоды.

### Backend и данные

- Next.js Route Handlers образуют REST-подобный HTTP API;
- PostgreSQL 17 в локальном `docker-compose.yml`;
- Prisma ORM 7.8 с `@prisma/adapter-pg`;
- явный `pg.Pool`: максимум 15 соединений по умолчанию, таймаут подключения 5 секунд,
  query/statement timeout 30 секунд;
- PostgreSQL одновременно служит основной БД, durable-очередью, rate limiter и источником ревизий
  для SSE;
- отдельный TypeScript worker обрабатывает очередь оценки и завершает просроченные контесты;
- локальное файловое хранилище реализует интерфейс `ObjectStorage`; его можно заменить
  S3-совместимым адаптером без изменения API посылок.

### Инструменты качества

- ESLint 9 с конфигурацией Next.js;
- `tsc --noEmit`;
- Prisma validate/generate/migrate deploy;
- Node test runner через `tsx`;
- HTTP smoke-тесты;
- отдельные интеграционные сценарии аватара, фото-посылки и очереди.

## 3. Физическая архитектура MVP

```text
браузер / установленная PWA
        |
        | HTTPS + JSON/form-data + SSE
        v
Next.js web-процесс
  |       |             |
  |       |             +--> приватный ObjectStorage (сейчас filesystem)
  |       |
  |       +--> PostgreSQL: сущности, сессии, аудит, rate limit, jobs
  |
  +--> создаёт EvaluationJob и сразу отвечает клиенту

отдельный judge-worker
  |
  +--> забирает job из PostgreSQL
  +--> читает фото из ObjectStorage
  +--> preprocess -> OCR -> structure -> scoring -> review
  +--> сохраняет Evaluation/JudgeModelRun/балл
  +--> после финальной партии запускает rating calculation
```

Web и worker не передают задания через память процесса. Поэтому рестарт web не теряет очередь, а
несколько web-инстансов могут работать с одной БД. Worker также можно масштабировать горизонтально:
claim job выполняется условным обновлением, а проверки одной посылки сериализованы.

## 4. Слои и структура репозитория

- `app/` — страницы App Router и HTTP route handlers;

- `server/` — бизнес-правила, запросы, сериализация, auth, rating, queue;

- `lib/` — presentation helpers и чистые функции;
- `types/` — DTO между сервером и UI;

- `tests/` — быстрые unit-тесты доменных инвариантов;

UI не импортирует Prisma напрямую. Server Components страниц могут обращаться к `server/` и Prisma,
а клиентские компоненты получают сериализованные DTO или вызывают API.

## 5. Модель данных

### Аккаунты и организации

- `User`: email, нормализованный уникальный ник, scrypt hash, описание, класс, роль, организация,
  рейтинг, настройки профиля и ссылки на аватар;
- `Organization`: уникальное нормализованное название, создатель и участники;
- `UserOrganizationHistory`: неизменяемая история переходов между организациями;
- `AuthSession`: случайный 256-битный bearer-token хранится в cookie, в БД лежит только SHA-256 hash
  и срок действия.

### Контестный домен

- `Contest`: расписание, продолжительность, статус, публичность, организация, правила и теги;
- `Problem`: условие, тема, рубрика проверки, исходный/абсолютный балл, decay и позиция A–E;
- `ContestRegistration`: уникальная пара contest/user;
- `ContestRatingSnapshot` и `ContestRatingSeed`: неизменяемый стартовый снимок состава, рейтингов,
  посева и ожиданий.

### Посылки и проверка

- `Submission`: автор, задача, статус, предварительный/финальный балл и публичность;
- `SubmissionFile`: storage key, MIME, размер, исходное имя и SHA-256;
- `SubmissionComment`: публичная/приватная история system/AI/admin;
- `Evaluation`: отдельный запуск предварительной или финальной оценки;
- `JudgeModelRun`: метрика каждого этапа — provider, latency, confidence, безопасный JSON output и
  ошибка;
- `EvaluationJob`: durable job, attempts, lease, retry time и связь с финализацией;
- `ContestFinalization`: агрегат финальной партии последних решений.

### Рейтинг, безопасность и аудит

- `RatingCalculation`: один версионированный расчёт на контест;
- `RatingChange`: место, балл, ожидание, delta и рейтинги участника;
- `AdminAction`: неизменяемый журнал административных изменений;
- `RateLimitWindow`: атомарные PostgreSQL-окна ограничения частоты.

Удаление связанных доменных записей в основном использует foreign keys и Cascade/Restrict/SetNull.
Файлы намеренно не хранятся в PostgreSQL.

## 6. Авторизация и аккаунт

### Регистрация

Пользователь указывает email, ник, пароль, необязательный класс и либо выбирает организацию, либо
создаёт новую. Сервер:

1. проверяет Origin и rate limit;
2. нормализует email/ник и валидирует диапазоны;
3. вычисляет scrypt hash с уникальной 16-байтовой солью;
4. одной транзакцией создаёт организацию при необходимости, пользователя и запись истории
   организации;
5. создаёт серверную сессию;
6. JSON-клиент получает user, HTML-form получает redirect в профиль.

Если аккаунт успел создаться, но создание сессии завершилось ошибкой, пользователь теперь получает
честное сообщение и redirect на вход, а не предложение повторно создать уже существующий аккаунт.
Конкурентные unique ошибки email, ника и организации различаются по полю.

### Сессии и пароль

- cookie: `HttpOnly`, `SameSite=Lax`, `Secure` в production, path `/`;
- срок сессии — 30 дней;
- cookie содержит случайный token, БД — только его hash;
- logout удаляет текущую серверную сессию и cookie;
- пароль ограничен 8–72 символами и хранится как параметризованный scrypt.

Не реализованы email verification, восстановление пароля, смена пароля, двухфакторная авторизация и
управление списком устройств. До публичного запуска минимально необходим reset-password flow.

## 7. Организации и профиль

Пользователь состоит ровно в одной организации и может сменить её в профиле; смена записывается в
историю. Администратор может менять роль и организацию любого пользователя и переименовывать
организации. Создание организаций доступно вошедшему пользователю и ограничено десятью в сутки на
аккаунт.

Профиль содержит:

- ник, описание, организацию и класс;
- текущий/максимальный рейтинг и звание;
- любимую тему;
- приватность класса и организации на публичном профиле;
- пять палитр и четыре рисунка обложки;
- JPEG/PNG/WebP-аватар до 5 МБ;
- историю рейтинговых контестов и график 0–3000.

Цвет ника всегда вычисляется по рейтингу и не подменяется акцентом профиля. Аватар публичен, имеет
версионированный immutable URL, а замена удаляет старый объект. Байты проверяются по сигнатуре и
заголовку изображения, включая лимит 40 мегапикселей/12000 px.

## 8. Жизненный цикл контеста

Состояния: `ANNOUNCED -> RUNNING -> FINISHED`.

### ANNOUNCED

- редактируются расписание, видимость, правила и пять задач;
- участники регистрируются до `startAt`;
- условия задач для участника скрыты;
- standings показывает предварительный посев по текущему рейтингу.

### Запуск

Запуск идёт только через специальный admin endpoint. Он:

1. требует ровно пять задач;
2. запрещает запуск раньше `startAt` и после `endAt`;
3. одной транзакцией создаёт стартовый rating snapshot;
4. переводит контест в `RUNNING`;
5. записывает audit action.

Общий PATCH больше не может обойти snapshot. После запуска расписание, видимость, правила и задачи
заморожены: изменение `startAt` задним числом ранее могло менять decay уже загруженных решений. UI
также блокирует эти поля.

### RUNNING

Посылка принимается только если одновременно выполняются:

- status равен `RUNNING`;
- `startAt <= now < endAt`;
- пользователь зарегистрирован или является admin;
- задача принадлежит контесту;
- пользователь имеет доступ к публичному/организационному контесту.

UI и API используют одну функцию жизненного цикла, поэтому форма больше не показывается после
фактического конца, даже если worker ещё не обновил status.

### FINISHED

Администратор может завершить тур досрочно. Кроме того, worker раз в 30 секунд находит просроченные
`RUNNING`-контесты и атомарно переводит их в `FINISHED`. Сразу создаётся финальная партия последних
посылок user/problem. После запуска разрешены только завершение, модерация, перепроверка и рейтинг.

Пока не реализован автоматический переход `ANNOUNCED -> RUNNING` по расписанию: старт является
осознанным действием администратора. Следующее ТЗ должно решить, оставить ручной старт или добавить
scheduler с preflight-проверкой.

## 9. Фото-посылка и приватность

Основной клиент отправляет файл как raw body, чтобы не зависеть от тяжёлого multipart parsing.
Сервер сначала проверяет сессию и пользовательский rate limit, и только потом читает тело. Поток
читается с жёстким пределом 15 МБ, поэтому поддельный или отсутствующий `Content-Length` не
позволяет бесконечно занимать память.

Проверяются:

- UUID контеста и задачи;
- права и временное окно;
- JPEG/PNG/WebP magic bytes;
- непустой размер и лимит 15 МБ;
- корректный заголовок и разумное разрешение;
- SHA-256 сохранённых байтов.

Фотография доступна только автору и администратору через endpoint с
`Cache-Control: private, no-store`. Публичная лента отдаёт ник, задачу, время, status и score, но не
storage key и не фото.

После сохранения объекта одна DB-операция создаёт Submission, SubmissionFile, первый system comment
и EvaluationJob. HTTP возвращает `201` без запуска OCR, то есть медленная модель не удерживает web
request.

## 10. Очередь, retries и финальная перепроверка

PostgreSQL-очередь хранит `QUEUED/PROCESSING/COMPLETED/FAILED`, attempts, `availableAt`, `lockedAt`,
workerId и error. Retry использует экспоненциальную задержку 5, 10, 20 секунд с потолком 5 минут; по
умолчанию максимум три попытки. Lease считается зависшим через 10 минут и возвращается в очередь.

Ключевой исправленный инвариант: одна посылка не оценивается двумя worker одновременно. Claim не
выбирает queued follow-up, пока для той же Submission есть PROCESSING job. Операции enqueue
сериализованы PostgreSQL advisory lock.

Если во время завершения тура preliminary job ещё:

- `QUEUED` — она повышается до `REJUDGE` и связывается с финализацией;
- `PROCESSING` — создаётся последовательная follow-up `REJUDGE`, которая ждёт завершения текущей;
- уже `REJUDGE` — повторная активная job не создаётся.

Если финальная job исчерпала попытки, финализация становится `FAILED`. Ручная кнопка перепроверки
теперь переиспользует failed job, сбрасывает attempts и возвращает связанную финализацию в `QUEUED`.
После последнего успешного job финализация становится `COMPLETED` и автоматически вызывает рейтинг.

Администратор не может изменить score/status, пока для посылки есть активная job: это защищает
ручной итог от немедленного перезаписывания worker.

## 11. Фактический evaluation pipeline

Pipeline разделён на заменяемые этапы:

1. `preprocess` — сейчас pass-through исходных байтов;
2. `OCR` — локальный Tesseract, последовательный fallback языков;
3. `structure` — признаки длины, формул, связок доказательства и вывода;
4. `scoring` — консервативная эвристика с верхней границей 55% доступного балла на preliminary;
5. `review` — confidence и флаг ручной проверки.

Низкая уверенность, короткий текст, ошибка OCR или геометрия переводят решение в `NEEDS_REVIEW`.
Каждый этап пишет `JudgeModelRun`.

Финальная проверка запускает тот же preliminary pipeline, затем два независимых эвристических
reviewer-расчёта и агрегатор среднего. Архитектурно это имитирует контракт «две модели + контрольная
модель», но фактически не является тремя сильными AI-моделями и не доказывает математическую
корректность.

Для реальных рейтинговых соревнований нельзя считать этот score точным. До релиза нужен vision/LLM
judge с версионированной схемой ответа, rubric-aware проверкой, набором эталонных решений и
обязательным human review для низкой уверенности. Текущий pipeline полезен как инфраструктурный
каркас и безопасный fallback, но не как окончательный судья.

## 12. Баллы и live-standings

Доступный максимум задачи в момент отправки:

```text
max(0, min(maxScore,
    baseScore - floor((submittedAt - startAt) / 5 минут) * decayPer5Min))
```

По каждой задаче в таблице учитывается только последняя посылка участника. Даже непроверенная
последняя посылка сразу заменяет старую и временно даёт ноль:

```text
finalScore ?? preliminaryScore ?? 0
```

Порядок:

1. totalScore по убыванию;
2. время последней учитываемой посылки по возрастанию с точностью БД;
3. user UUID как детерминированный последний tie-break.

Этот tie-break теперь одинаков в standings и рейтинговой формуле. Строка показывает preliminary ->
final, разницу, максимум в момент отправки, историю и комментарии. SSE раз в четыре секунды сначала
проверяет короткую revision; весь payload перестраивается только при изменении. Heartbeat идёт раз в
20 секунд. Скрытая вкладка закрывает EventSource, UI использует FLIP-анимацию перестановок и
анимированные числа.

## 13. Рейтинг `placement-v2`

До первого рейтингового контеста фактический рейтинг равен 0, но UI показывает `—`. Верхняя граница
— 3000, delta одного тура — от −500 до +500. Один активный участник рейтинг не получает.

При запуске фиксируются `ratingAtStart`, seed и expected place. Вероятность ожидания основана на
логистической паре со scale 400:

```text
P(opponent ahead) = 1 / (1 + 10 ^ ((ratingParticipant - ratingOpponent) / 400))
expectedPlace = 1 + sum(P(opponent ahead))
```

Фактическая производительность:

```text
actualScore   = (participants - actualPlace) / (participants - 1)
expectedScore = (participants - expectedPlace) / (participants - 1)
performance   = actualScore - expectedScore
deltaBase     = round(500 * contestWeight * performance)
```

`contestWeight` — среднее ограниченных коэффициентов длительности, суммы максимальных баллов и
размера активного состава. Полноценный тур стремится к весу 1, маленький/короткий влияет слабее.

Новичок со стартовым рейтингом 0 получает onboarding issuance:

```text
contestWeight * (100 + 100 * actualScore), минимум +25
```

Для уже рейтинговых игроков базовая сумма delta балансируется примерно к нулю; добавляется
контролируемый системный рост +1 на активного участника. Алгоритм перераспределяет остаток с учётом
пола 0, потолка 3000 и лимита 500.

Защиты расчёта:

- только FINISHED;
- финализация и все активные rejudge должны закончиться;
- минимум два участника с посылками;
- старый контест нельзя впервые считать после более нового;
- пересчёт раннего тура блокируется, если уже применены последующие изменения;
- повторный расчёт не удваивает delta;
- `maxRating` восстанавливается из полной истории.

Публичная `/rating` содержит всех пользователей, сортируется по рейтингу и нику, имеет фильтр
организации, пагинацию 50, аватары, цвет ранга и движение мест после последнего рассчитанного тура.
Переименование организации также теперь меняет SSE revision.

## 14. Админ-панель

Маршрут `/admin` защищён server-side role check. Реализованы:

- dashboard со статистикой;
- конструктор контеста и пяти задач;
- запуск/завершение и ручной пересчёт рейтинга;
- просмотр фото, AI output/confidence и ручная коррекция score;
- повторная оценка;
- управление ролями/организациями пользователей;
- создание и переименование организаций;
- журнал AdminAction;
- мониторинг queue/finalization/storage/needs-review/failed jobs.

Админский audit покрывает создание/изменение контеста и задач, запуск, изменения
пользователя/организации, коррекции и rejudge, рейтинг. Обычная смена профиля самим пользователем не
входит в AdminAction, но история организации сохраняется отдельно.

## 15. PWA, темы и offline

Manifest содержит standalone mode, scope/id, PNG 192/512, maskable icon и Apple touch icon. Service
worker регистрируется только в production. Есть prompt установки, iOS-инструкция и управляемое
обновление новой версии.

Offline стратегия network-first для безопасных публичных страниц и cache-first для versioned static
assets. API, фото, приватные профили и RSC-запросы не кэшируются. В ходе аудита из navigation cache
удалены `/contests`, `/login` и `/register`: эти маршруты зависят от cookie/redirect и могли
сохранить персонализированный HTML на общем устройстве. Cache key теперь включает полный Request,
включая query string.

Темы `system/light/dark`, плотность таблиц и motion preference хранятся только на устройстве в
localStorage и применяются до hydration. Режим reduced motion отключает не только CSS, но и
программные Web Animations.

## 16. Security posture

Сейчас есть:

- серверная валидация всех мутаций;
- Origin check для POST/PATCH/DELETE;
- SameSite HttpOnly session cookie;
- scrypt и timing-safe compare;
- role/ownership checks на приватные фото и evaluation details;
- UUID validation до запросов;
- magic/header/dimension/size validation изображений;
- per-client rate limit auth и per-user rate limit upload/avatar/org create;
- параметры Prisma вместо конкатенации SQL;
- `nosniff`, frame deny, referrer policy, permissions policy и COOP;
- приватный `no-store` для решения;
- audit административных изменений.

До публичного релиза нужны:

- password reset и email verification;
- политика первого/последнего администратора и recovery admin access;
- production CSP с nonce, HSTS на TLS-терминаторе и проверка proxy headers;
- S3 private bucket + signed/internal reads вместо локального диска;
- антивирус/декодирование и нормализация изображений в sandbox;
- регулярный dependency advisory scan в CI;
- retention/delete policy для аккаунтов, фото и персональных данных;
- privacy policy/согласие, поскольку платформа ориентирована на школьников.

Внешний `npm audit` в этом прогоне не выполнялся: среда отклонила отправку dependency metadata во
внешний advisory service без отдельного явного согласия владельца. Локальные lint/type/build
проверки выполнены.

## 17. Надёжность и эксплуатация

`/api/health` проверяет DB, storage, stale jobs, возраст старейшей queued job и просроченные
RUNNING-контесты. Если job ждёт дольше 120 секунд (настраивается `HEALTH_MAX_QUEUE_AGE_SECONDS`),
есть stale lease или scheduler не завершил контест, endpoint возвращает `503 degraded`. Раньше
остановленный worker мог оставаться незаметным при зелёном health.

Worker обрабатывает SIGINT/SIGTERM, закрывает Prisma и использует `allowExitOnIdle`, поэтому
корректно завершается без ожидания pool timeout.

Backup script создаёт PostgreSQL custom dump и tar всего object storage, включая submissions и
avatars, затем удаляет локальные копии старше retention. Само наличие скрипта не заменяет production
cron, внешнее хранилище backup и регулярный restore drill.

## 21. Минимальный production runbook

Необходимы четыре долговечных ресурса: web-процесс, judge-worker, PostgreSQL и object storage.
Вариант с одним VPS допустим для закрытого пилота, если web и worker управляются systemd/Docker с
автоматическим restart, а файлы и backup лежат на постоянном volume.

Обязательная последовательность релиза:

```bash
npm ci
npm run db:deploy
npm run build
npm run start
# отдельный процесс
npm run worker:judge
```

Минимальные переменные:

- `DATABASE_URL` — production PostgreSQL со SSL по требованиям провайдера;
- `DATABASE_POOL_SIZE` — учитывать сумму web + всех worker-инстансов;
- `SUBMISSION_STORAGE_DIR` для persistent filesystem или конфигурация будущего S3 adapter;
- `HEALTH_MAX_QUEUE_AGE_SECONDS` — допустимая задержка judge;
- `TESSERACT_BINARY` и `TESSERACT_LANGUAGES` для локального fallback;
- `BACKUP_DIR` и `BACKUP_RETENTION_DAYS` для cron backup.

Перед открытием трафика: запросить `/api/health`, выполнить `test:smoke`, один avatar smoke и один
submission smoke с `SMOKE_BASE_URL` стенда. Worker должен быть запущен постоянно, иначе web
продолжит принимать решения, но health станет degraded после порога очереди. После миграций нельзя
запускать старую сборку, если она не совместима с новой схемой.

Ежедневно нужно сохранять DB + object storage вне основного сервера. Раз в месяц — восстанавливать
обе части на отдельном окружении и проверять соответствие `SubmissionFile.storageKey` реальным
объектам. Логи должны хранить request/job correlation id, но не пароли, session token, фото или
полный OCR-текст.
