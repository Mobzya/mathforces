# Производительность и автоматизация

## Загрузка решения

Область «Сделать фото или выбрать файл» использует нативный прозрачный `input[type=file]`,
расположенный поверх всей карточки. Выбор файла не зависит от гидрации React и работает сразу после
отрисовки HTML. Атрибут `capture` не навязывается: мобильная ОС сама предлагает камеру, галерею и
файловый менеджер.

После выбора браузер показывает локальный preview. При отправке web-процесс:

1. проверяет лимит, сигнатуру JPEG/PNG/WebP и доступ к контесту;
2. сохраняет объект и одну транзакцию с Submission, SubmissionFile и EvaluationJob;
3. немедленно возвращает `201`;
4. не запускает OCR или оценивание внутри HTTP lifecycle.

Сессия проверяется до чтения тела. Raw body читается потоком с жёстким лимитом 15 МБ даже при
отсутствующем или ложном `Content-Length`. Дополнительно проверяются заголовок и разрешение
изображения: максимум 40 мегапикселей и 12000 px по стороне.

Всю оценку выполняет только отдельный `npm run worker:judge`. Это исключает двойные AI-комментарии,
конкуренцию web/worker за одну посылку и зависание навигации после загрузки.

## Live и polling

- standings и общий рейтинг продолжают проверять изменения каждые четыре секунды, но сначала
  выполняют один короткий revision-запрос;
- тяжёлый payload с результатами и историями строится только при изменении ревизии;
- раз в 20 секунд отправляется дешёвый SSE heartbeat;
- скрытая вкладка закрывает EventSource и восстанавливает его при возврате;
- лента посылок использует последовательный `setTimeout` вместо `setInterval`, поэтому медленный
  запрос никогда не перекрывается следующим;
- polling ленты приостанавливается в скрытой вкладке.

## Worker и PostgreSQL

- поиск просроченных контестов выполняется раз в 30 секунд, а не перед каждым job;
- освобождение зависших jobs выполняется не чаще раза в минуту;
- повторная попытка обновляет job и submission последовательными запросами в одной интерактивной
  транзакции;
- advisory lock сериализует enqueue одной посылки, а worker не берёт follow-up, пока для неё уже
  есть PROCESSING job;
- web и worker используют явный PostgreSQL pool с таймаутами соединения и запроса; размер задаётся
  `DATABASE_POOL_SIZE` и по умолчанию равен 15.

## Локальная разработка

Проект сохраняет webpack для `npm run dev`: на текущей файловой системе Turbopack сам сообщил о
медленном диске и показал худшее холодное время. Dev компилирует новый маршрут при первом открытии,
поэтому первая навигация всё ещё не отражает production latency. Реальную скорость следует проверять
через `npm run build`, `npm run start` и smoke-сценарии.

## Проверки

```bash
npm run test:smoke
npm run test:submission
npm run worker:judge:once
```

`test:submission` проверяет реальный HTTP upload, состояние `QUEUED` и наличие EvaluationJob до
запуска worker. Это специально гарантирует, что дорогое оценивание не вернулось в web-процесс.
