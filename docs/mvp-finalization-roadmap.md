# Mathforces — план финализации рабочего MVP

Дата сверки: 2 августа 2026 года.

Документ сопоставляет новый `deep-research-report (1).md` с фактическим проектом. При конфликте
требований действует последнее решение владельца: новый пользователь имеет `currentRating = 0` и
`maxRating = 0`, а интерфейс до первого рейтингового контеста показывает `—` и звание «Без
рейтинга».

## 1. Целевая граница MVP

Цель текущей итерации — закрытый школьный пилот, в котором можно безопасно провести настоящий
контест от регистрации до рейтинга. Автоматическая локальная эвристика является помощником
проверяющего, а не математическим арбитром. Пока не подключён и не откалиброван внешний vision/LLM
judge, каждый предложенный ею финальный балл требует подтверждения администратора. Благодаря этому
рейтинг строится только по проверенным человеком результатам.

Для одного VPS MVP состоит из четырёх долговечных частей:

1. Next.js web/API;
2. judge-worker и scheduler;
3. PostgreSQL;
4. постоянный том с приватными изображениями.

Переход на private S3 и внешний judge выполняется заменой адаптеров после выбора провайдера, бюджета
и production-площадки. Эти внешние решения нельзя надёжно угадать в локальном коде.

## 3. Найденные несостыковки и исправления

### Критические

- `NEEDS_REVIEW` раньше не останавливал завершение финального пакета. Теперь у финализации есть
  отдельное состояние `NEEDS_REVIEW`, а rating API принимает только `COMPLETED`.
- Эвристическая финальная оценка могла считаться математически достоверной. Теперь она всегда
  является предложением и ждёт ручного подтверждения.
- `REJECTED` сохранял старые числовые оценки и мог продолжать влиять на сумму. Теперь аудиторские
  поля сохраняются, но вклад в standings/rating равен нулю.
- Ручная коррекция после публикации не имела версии результата. Добавлены `Contest.resultsRevision`
  и `RatingCalculation.resultsRevision`; устаревший расчёт виден администратору и автоматически
  пересчитывается, если история последующих туров это допускает.
- Администратор мог вручную назначить `QUEUED/PROCESSING` без job. Эти статусы теперь изменяет
  только очередь; ручной интерфейс работает с результатными состояниями.

### Операционные

- Раньше не было одной кнопки восстановления failed finalization. Теперь можно повторить только
  ошибки или перепроверить все последние решения.
- Контест зависел от присутствия администратора в момент старта. Worker теперь атомарно запускает
  готовые туры по расписанию и фиксирует rating snapshot.
- Списки имели немые пределы 100/200. Публичная лента получила cursor, а контесты и админские
  посылки — поиск и страницы.
- Не было штатной смены/восстановления пароля. Добавлены оба сценария с отзывом сессий, rate limit,
  одноразовым SHA-256 token и аудитом выдачи.
- CSV отсутствовал. Экспорт теперь не содержит фото/OCR и защищён от spreadsheet formula injection.

## 4. Спринты финализации

### Спринт A — доменные инварианты и достоверность (выполнен)

- ручной gate финальной проверки;
- версия результатов и устаревшего рейтинга;
- нулевой вклад отклонённой посылки;
- безопасные статусы ручной модерации;
- обязательная причина коррекции;
- unit/integration проверки этих правил.

Критерий: рейтинг не может появиться до подтверждения всех спорных финальных результатов и никогда
не использует отклонённую оценку.

### Спринт B — пользовательский и аккаунтный MVP (выполнен)

- смена пароля с проверкой текущего;
- завершение старых сессий;
- одноразовая admin-assisted recovery;
- cursor-пагинация публичных посылок;
- поиск/фильтр/пагинация контестов;
- сохранение правила `0 -> —` во всех рейтинговых представлениях.

Критерий: участник проходит регистрацию, вход, восстановление, регистрацию на тур, загрузку и
просмотр всей истории без скрытого лимита первых записей.

### Спринт C — операционный MVP администратора (выполнен)

- повтор failed jobs и rejudge всех последних решений;
- безопасный CSV результатов и рейтинга;
- пагинация и поиск посылок;
- наблюдаемая блокировка rating при ручном review;
- полный audit новых административных операций.

Критерий: администратор способен восстановить сбой и закончить тур без ручных SQL-команд.

### Спринт D — эксплуатация и рост (выполнен для одного VPS)

- scheduler автоматического старта и завершения;
- health/monitoring пропущенных стартов;
- Dockerfile с Tesseract;
- production Compose: migrate, web, worker, PostgreSQL и persistent volumes;
- GitHub Actions: migrations, lint, typecheck, unit, queue и build;
- актуализированные переменные окружения и worker runbook.

Критерий: web и worker разворачиваются отдельно и переживают рестарты без потери job или изображений
на persistent volume.

### Спринт E — релизная репетиция (выполнен локально)

- применить все миграции на чистой и текущей БД;
- lint, typecheck, unit и queue integration;
- production build;
- HTTP smoke регистрации/входа/профиля/доступа;
- avatar и real-image submission smoke;
- полный сценарий двух участников до manual review и rating;
- проверка целостности БД и финальный runbook пилота.

Критерий: воспроизводимый тест проходит без queued/processing/failed хвостов, а нулевой рейтинг
нового аккаунта нигде не отображается числом.

Фактический результат:

- Prisma schema valid, 16/16 миграций применены;
- ESLint и TypeScript прошли;
- unit: 22/22;
- queue integration и двухпользовательский full-cycle прошли;
- account security smoke подтвердил `rating = 0`, смену пароля, отзыв сессий и одноразовое
  восстановление;
- production build прошёл со всеми маршрутами;
- HTTP/PWA/health smoke: 9/9;
- avatar и настоящий PNG submission smoke прошли;
- race удаления тестовой job при работающем worker воспроизведён, исправлен и повторно проверен без
  падения worker;
- 100 одновременных смешанных read-запросов: 0 ошибок; p95 около 2,5 с;
- 100 одновременных запросов API рейтинга: 0 ошибок; p95 около 0,57 с;
- одиночный запрос API рейтинга: около 188 мс;
- integrity: queued=0, processing=0, failed=0, stale jobs=0, expired running=0, submissions without
  files=0, stale ratings=0;
- `docker compose ... config --quiet` для production-конфигурации прошёл.

`npm audit` локально не запускался: среда не разрешила передавать dependency metadata во внешний
advisory service без отдельного согласия. Workflow CI готов для добавления отдельного dependency
scan после выбора политики доступа.

## 5. Что остаётся внешним решением после рабочего закрытого MVP

1. Выбор vision/LLM provider и бюджета, затем benchmark на размеченных школьных решениях. До этого
   human gate отключать нельзя.
2. Домен, TLS, production secret storage и конкретный сервер/облако.
3. Private S3 provider, lifecycle и off-host backup/restore drill.
4. Политика хранения фото и согласия для несовершеннолетних.
5. Почтовый провайдер, если вместо admin-assisted recovery нужна полностью самостоятельная email
   verification/reset.

Эти пункты требуют credentials, юридических правил или продуктового выбора; они не блокируют
закрытый модерируемый пилот, но блокируют обещание полностью автономного публичного судейства.
