# Sprint 9 — подготовка к росту

## Очередь и worker

`EvaluationJob` — долговечная PostgreSQL-очередь с режимом проверки, числом попыток,
экспоненциальной задержкой, lease-блокировкой и возвратом зависших задач. Несколько worker-процессов
могут безопасно конкурировать за задания. Проверки одной Submission сериализованы: queued follow-up
не может быть взят, пока другая job той же посылки имеет статус PROCESSING. Если preliminary ещё не
началась при завершении тура, она переиспользуется как REJUDGE; если уже обрабатывается, финальная
job выполняется строго следом. Failed-финализация восстанавливается ручной перепроверкой связанной
посылки.

Web только создаёт задания. Обработка запускается отдельной командой:

```bash
npm run worker:judge
```

`ContestFinalization` объединяет финальные проверки контеста. При завершении выбираются последние
посылки каждого участника по каждой задаче. Рейтинг рассчитывается только после успешного завершения
всей партии.

Worker также автоматически переводит просроченные `RUNNING`-контесты в `FINISHED`.

Финальная проверка использует два независимых эвристических reviewer-прохода и контрольный
агрегатор. Она сохраняет `finalScore`, но не создаёт отдельное сообщение в истории посылки.
Live-таблица показывает `preliminaryScore → finalScore` и разницу при наведении или открытии строки.

## Баллы в реальном времени

Максимум задачи в момент отправки:

```text
max(0, min(maxScore, baseScore - floor(elapsedMinutes / 5) × decay))
```

На странице контеста и в standings отображаются:

- полученный балл и максимум на момент отправки;
- доступный сейчас максимум и абсолютный максимум;
- оставшееся время до секунды;
- прогресс финальной перепроверки.

## Масштабирование

- web и worker не хранят состояние заданий в памяти и масштабируются отдельно;
- фотографии доступны через `ObjectStorage`, поэтому локальный адаптер можно заменить S3-совместимым
  без изменения API посылок;
- добавлены индексы очереди, последних посылок и регистраций;
- список организаций имеет короткий TTL-кэш; интерфейс кэша изолирован для последующей замены на
  Redis;
- SSE остаётся транспортом live-таблицы, а источник данных не зависит от конкретного web-процесса.

## Защита и наблюдаемость

- PostgreSQL rate limit для входа, регистрации и загрузки решений;
- `/api/health` проверяет БД, storage, очередь, возраст старейшей job, зависшие jobs и просроченные
  RUNNING-контесты;
- `/admin/monitoring` показывает очередь, возраст старейшего задания, ошибки, ручную проверку и
  задержку БД;
- административные изменения продолжают писаться в `AdminAction`;
- ошибки worker сохраняются в `EvaluationJob`, а не только в stdout.

## Резервное копирование

Команда:

```bash
npm run backup:create
```

создаёт PostgreSQL custom dump и архив object storage. Переменные:

- `BACKUP_DIR`;
- `BACKUP_RETENTION_DAYS` (по умолчанию 14);
- `SUBMISSION_STORAGE_DIR`;
- `DATABASE_URL`.

В production команду следует запускать ежедневным cron/systemd timer, хранить копии вне основного
сервера и ежемесячно проверять восстановление на отдельной БД. Для S3 необходимо включить versioning
и lifecycle policy.
